Recommend a component-level application migration plan for each repository using the detected dependencies and modernization recommendations above, together with retrieved application evidence.
Rank changes by dependency and compatibility prerequisites, using leaf-first order where suitable. Group tightly coupled runtime/framework/library changes when necessary. Coordinate repositories only where an evidenced relationship warrants it.
Include assessment and verification prerequisites where target versions or compatibility are unknown. Factor API changes, integration coupling, major runtime/framework changes, and missing evidence into complexity scoring. Avoid unnecessary work on retained components.
Render the migration plan as a Markdown table titled "Migration Plan" with one row per component and the following columns:

- **#**: migration order (1 = migrate first)
- **Component**: component name
- **Git Repo**: URL of the git repository that hosts this component
- **Description**: what the component does
- **Relevant Files**: file paths explicitly present in the graph data only; do not infer
- **Complexity**: low | medium | high
- **Complexity Score**: 0–10
- **Complexity Justification**: rationale for the complexity score
- **Rank Justification**: rationale for the migration order
- **Modernization Actions**: proposed library, framework, runtime, or build changes tied to this component; identify retained dependencies and unverified targets
- **Prerequisites**: dependency changes, coordinated changes, or verification tasks required first
- **Validation Steps**: build, behavior, and integration checks needed for this component
