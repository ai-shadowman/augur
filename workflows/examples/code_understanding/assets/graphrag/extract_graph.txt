-Target activity-
You are an AI assistant that helps analyze software codebases and extract dependency information.

-Goal-
Given a text document describing a software artifact — which may be source code in any programming language, a configuration file, an infrastructure definition, or a build script — identify all software entities and the relationships between them.

Every document begins with a header of the form:
  "This file is located at <path> from repository url <git_repo_url>, repository slug <git_slug_value>, multi_repo <true|false>"
  The header may optionally end with: ", runtime <runtime_components>" (e.g. ", runtime Python 3.12")
Use <path> to name the module entity for this document. Do not emit a repository entity and do
not repeat the url in descriptions: the repository, its url, its slug, its runtime and every
BELONGS_TO edge are added from the header after extraction. Report what the code does.

-Steps-
1. Identify all entities. For each identified entity, extract the following information:
- entity_name: Most specific identifier available for the entity.
  If multi_repo is true (from the document header), prefix with <git_slug>:: to
  avoid cross-repo name collisions
  (e.g., acme-payments-main::com.acme.payments.PaymentService); otherwise use the bare name.
  Use the relative file path for modules
  (e.g., src/main/java/com/acme/PaymentService.java), fully qualified names for
  classes/functions (e.g., com.acme.PaymentService, com.acme.PaymentService.getPayment),
  key-path notation for config files (e.g., spring.datasource.url). External dependencies
  shared across repos are never prefixed.
- entity_type: One of the following types: [{entity_types}]
- Before typing an imported or referenced name, place it in one of three layers:
  a. APPLICATION CODE — defined in THIS repository. Type it module, class or function.
     Never library or stdlib_module, however it was imported.
  b. PLATFORM — a module of the language's own standard library. Type it stdlib_module.
  c. PACKAGE — a third-party distribution. Type it library, named for the distribution.
     If a manifest or build file declares a version, add a sentence "Version: <spec>." to
     the description, using the spec exactly as declared.
  If unsure between b and c, use library. Never leave entity_type blank.
- entity_description: Comprehensive description of the entity's role, responsibilities, and key behaviors. Always refer to the entity using its exact original casing as found in the source (e.g. write "game.py" not "GAME.PY" if the source file is named game.py).

2. From the entities identified in step 1, identify all pairs of (source_entity, target_entity) that are *clearly related* to each other.
For each pair of related entities, extract the following information:
- source_entity: name of the source entity, as identified in step 1
- target_entity: name of the target entity, as identified in step 1
- relationship_description: begins "<source_entity> <TYPE> <target_entity>", TYPE being exactly one
  of the Relationship Types below, in capitals; then one clause of explanation. The source is the
  entity that imports, inherits, calls, uses or depends.
- relationship_strength: a numeric score indicating strength of the relationship between the source entity and target entity
For dependencies that cross repository boundaries, TYPE is CROSS_REPO_IMPORTS or CROSS_REPO_DEPENDS_ON.
Do not emit a relationship stating where something is defined; AUGUR writes those from the source.

######################
-Entity Types-
######################
This catalogue covers every type AUGUR can configure. Only the types in
[{entity_types}] are available for this run; if a type below is not in that
list, do not emit it.

- module: A single source file or compilation unit. entity_name = relative file path as found in the "This file is located at" annotation (e.g., src/main/java/com/acme/PaymentService.java, src/utils/my_service.py).
- class: A class definition. entity_name = fully qualified class name (e.g., com.acme.PaymentService, my_module.MyClass).
- function: A function or method. entity_name = fully qualified name including module and class where applicable (e.g., com.acme.PaymentService.getPayment, my_module.fetch_data, my_module.MyClass.my_method).
- package: A fully qualified language-specific namespace or directory that groups related modules or classes, or file path for Javascript/Typescript
- library: A third-party distribution the repository depends on, named for the distribution rather than any symbol inside it (e.g., kombu, requests, org.springframework.web). `from kombu.clocks import LamportClock` is the library kombu, not kombu.clocks and not LamportClock. Carries a version when one is declared. Never prefixed with git_slug
- stdlib_module: A module of the language's own standard library (e.g., logging, socket, java.util). Versioned by the runtime, never independently. Never prefixed with git_slug
- config_file: A configuration file (e.g., application.yaml, .env, terraform.tfvars)
- service: A configured service or infrastructure component (e.g., spring.datasource)
- variable: An environment variable or configuration property

######################
-Relationship Types-
######################
- IMPORTS: Module A imports Module B within the same repository
- INHERITS: Class A inherits from Class B
- CALLS: Function A calls Function B
- USES: Module A uses functionality from Module B
- DEPENDS_ON: Generic dependency relationship within the same repository
- CROSS_REPO_IMPORTS: Module A in one repo imports Module B from a different repo
- CROSS_REPO_DEPENDS_ON: Module A in one repo depends on Module B from a different repo

######################
-Output Format-
######################
No preamble, no explanation, no markdown fences — tuples only.
Two tuple types:

("entity"<|><entity_name><|><entity_type><|><entity_description>)
("relationship"<|><source_entity><|><target_entity><|><relationship_description><|><relationship_strength>)

End every tuple with {record_delimiter} on its own line, including the last tuple you
emit. If you are asked to continue and add more tuples, terminate those the same way.
After the final {record_delimiter}, emit {completion_delimiter} on its own line.

CRITICAL — Name an imported module exactly as the import statement spells it. Do not rewrite it
as a file path and do not infer where the file lives from the location of the file importing it.
Only the path in this document's own header may be written as a path.

WRONG:  ("entity"<|>celery/worker/registry.py<|>module<|>...)  ← this file is celery/worker/__init__.py and says `from celery import registry`
WRONG:  ("entity"<|>src/utils/helpers.py<|>module<|>...)       ← import says `from myapp import helpers`; the path was guessed
CORRECT:("entity"<|>celery.registry<|>module<|>...)
CORRECT:("entity"<|>myapp.helpers<|>module<|>...)

This holds for a relative import too: keep its leading dots. In celery/app/base.py,
`from ..datastructures import X` is ..datastructures. Resolving the dots needs the
package this document sits in, which is a calculation on the header path and is done
after extraction. Two attempts at having the model do it instead produced
celery.app.base.datastructures and src/celery/app/base.py.

CRITICAL — An attribute read off a variable is not an entity. `self.conf.EMAIL_HOST`
is a configuration key being read, not a declared name, and SELF is not a namespace.
Emit an entity only for something the document declares or imports.

CRITICAL — Use fully qualified names for module, class, and function entities. Never use bare names:

WRONG:  ("entity"<|>my_service.py<|>module<|>...)      ← bare filename; annotation says "located at src/utils/my_service.py"
WRONG:  ("entity"<|>play<|>function<|>...)             ← bare name; source is in `game.py`
WRONG:  ("entity"<|>PaymentService<|>class<|>...)      ← bare name; package is `com.acme`
WRONG:  ("entity"<|>getPayment<|>function<|>...)       ← bare name; class is `com.acme.PaymentService`
CORRECT:("entity"<|>src/utils/my_service.py<|>module<|>...)
CORRECT:("entity"<|>game.play<|>function<|>...)
CORRECT:("entity"<|>com.acme.PaymentService<|>class<|>...)
CORRECT:("entity"<|>com.acme.PaymentService.getPayment<|>function<|>...)

CRITICAL — Layer entities at the right granularity. Name the distribution or the module,
never a symbol inside one, and never file your own code as someone else's:

WRONG:  ("entity"<|>kombu.clocks<|>library<|>...)          ← a symbol inside a distribution
WRONG:  ("entity"<|>kombu.pools.ProducerPool<|>library<|>...)
CORRECT:("entity"<|>kombu<|>library<|>...)                 the distribution, once
WRONG:  ("entity"<|>basestring<|>stdlib_module<|>...)      ← a language builtin, not a module
WRONG:  ("entity"<|>time.sleep<|>stdlib_module<|>...)      ← a function inside a module
CORRECT:("entity"<|>time<|>stdlib_module<|>...)            the module, once
WRONG:  ("entity"<|>celery.worker.utils.timeutils<|>library<|>...)  ← defined in THIS repository
CORRECT:("entity"<|>celery/worker/utils/timeutils.py<|>module<|>...)

Language builtins (isinstance, map, len, basestring) are not entities at all. Skip them.

CRITICAL — Do not type a name as stdlib_module on the strength of the name alone. A name that
matches a standard library module can still be a third-party backport pinned in a manifest;
`multiprocessing==2.6.2.1` in a requirements file is a declared distribution, so it is a library.
If the document declares the name in a manifest, it is a library whatever it is called.
